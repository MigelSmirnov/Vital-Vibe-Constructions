# Передача локальному агенту: публикация на VPS

Владелец 2026-09-13 выбрал перенос на VPS и поручил выполнить его локальному агенту, у которого есть доступ к серверу. Повторное разрешение на сам деплой не требуется. Текущая сессия production и DNS не меняла.

## Какую версию брать

- Репозиторий: `MigelSmirnov/Vital-Vibe-Constructions`.
- Ветка с одобренными статьями и фото: **`agent/solar-collector-port`**.
- Начать с `AGENTS.md`, обязательных контрактов и `HANDOFF.md`.
- Забрать актуальную удалённую ветку в отдельный чистый checkout; записать полный `git rev-parse HEAD` как release SHA. Не собирать из старого `main`, корня репозитория или другой ветки `agent`.
- Корень публичного релиза — содержимое `.deploy-dist`, сформированное builder. Исходники, `task/`, секреты и репозиторий на веб-сервер не публиковать.

Одобрены каталоги статей ES/EN/RU, солнечный коллектор с анимацией v3 и двумя фото, исходная полная статья о покраске, полная статья о стоимости ремонта с разделами про полы и фото. Не превращать статьи обратно в краткие отчёты. Дополнительные статьи про электрику, сантехнику и ванную не являются условием запуска.

## Что проверено и что остаётся

Полные проверки сайта и навигация/статьи в Netlify preview проходили. Preview не является production-релизом. В этой сессии нет `cwebp` и Caddy, поэтому свежая полная production-сборка с WebP и проверка конфигурации Caddy остаются обязательными локальными шагами. Не брать старую `.deploy-dist` или старый CI artifact.

В `deploy/vps/Caddyfile` заменён `X-Frame-Options DENY` на `SAMEORIGIN`: интерактивная схема `/interactive/solar-collector-v3.html` должна открываться внутри статьи на том же домене. Проверить это именно через Caddy, включая `?lang=es`, `en`, `ru`.

## Сборка локально или в CI

Нужны Node.js 20, Git, Bash, tar, ImageMagick (`convert`), WebP (`cwebp`). В Ubuntu/Debian пакеты изображений называются `imagemagick` и `webp`; устанавливать на машине сборки. На VPS для раздачи готового сайта Node.js не нужен.

В чистом checkout, с остановкой при любой ошибке:

```bash
set -euo pipefail
command -v node
command -v convert
command -v cwebp
git rev-parse HEAD
node tools/checks/run.mjs
git diff --exit-code
node tools/deploy/build-vps-bundle.mjs
node tools/deploy/validate-vps-bundle.mjs
tar -C .deploy-dist -czf vps-site-bundle.tgz .
sha256sum vps-site-bundle.tgz
```

Альтернатива: вручную запустить `VPS bundle check` на указанной ветке, дождаться успеха и скачать `vps-site-bundle` именно для записанного SHA. Этот workflow собирает архив, но ничего не публикует. Проверить `DEPLOYMENT_COMMIT` в архиве и соответствие release SHA.

## Перенос

1. Прочитать `architecture/vps-migration-plan.md` и `architecture/vps-security-plan.md`. Проверить реальный VPS, ОС, SSH host key, deploy-пользователя и существующие сайты. Сохранить действующую конфигурацию Caddy и предыдущий release target. Не перезаписывать конфигурацию чужих сайтов.
2. Домен зарегистрирован у **DonDominio**. Проверить авторитетные NS и фактическую DNS-зону. Текущий сайт публикуется GitHub Pages из `main` (успешный workflow от 2026-09-06); точная настройка папки `/root` коннектором не прочитана. Сохранить текущие A/AAAA/CNAME для apex и www для отката.
3. Скопировать новый архив и release helpers на VPS, сверить SHA-256. Подготовить `/srv/vital-vibe/releases` с правами deploy-пользователя и чтением для Caddy. Перед активацией проверить распакованный релиз во временном document root; особенно если на VPS уже есть сайт.
4. Использовать `bash deploy/vps/install-release.sh /path/to/vps-site-bundle.tgz RELEASE_ID`. Скрипт переключает `/srv/vital-vibe/current` сразу, поэтому запускать после предварительной проверки. Сохранить прежний release ID для `rollback-release.sh`.
5. Интегрировать шаблон Caddy в реальную конфигурацию, выполнить `caddy validate --config /path/to/Caddyfile --adapter caddyfile` и предварительную проверку через Caddy до DNS cutover. Не объявлять простой файловый preview проверкой production headers. Проверить текущие пути/редиректы; архив не содержит конфигурацию сервера, её нужно установить отдельно.
6. После успешного предварительного просмотра направить apex на VPS. AAAA менять только при работающем IPv6; не оставлять старый адрес, ведущий на другой хостинг. www настраивать по подтверждённой текущей политике. Сохранить MX/TXT и **`app.vitalvibeconstruction.com`**: там отдельный электрический планировщик.
7. Перезагрузить Caddy штатно, проверить HTTPS/сертификат и HTTP→HTTPS. GitHub Pages пока оставить доступным для отката DNS.

## Приёмка после переноса

- `DEPLOYMENT_COMMIT` соответствует release SHA; новый главный экран на `/`, `/en/`, `/ru/`.
- Все маршруты актуального `sitemap.xml` открываются; не использовать старое число «8 маршрутов» из исторического плана.
- `/articulos/`, `/en/articles/`, `/ru/articles/`: по четыре опубликованные статьи, карточки и обратные ссылки работают.
- `/ru/articles/pokraska-sten-cena-podgotovka/`: полный текст, 10 разделов, два фото, 4–6 €/м² только работа по подготовленной стене.
- `/ru/articles/vyravnivanie-pola-pered-ukladkoy/`: полная статья о стоимости ремонта, 11 разделов, шесть фото, пример около 14 см на 10 м.
- `/articulos/conexion-colector-solar/`: встроенная v3 работает; переключения схемы/языка работают и нет отказа iframe из-за заголовков.
- CSS, фото, WebP, контакты и планировщик открываются. Галерея сохраняет 39 фото; на телефоне нет горизонтального переполнения.
- `robots.txt`, sitemap, canonical, юридическая страница и исторические редиректы корректны.

При проблеме откатить symlink на предыдущий релиз; при неудаче переноса хостинга восстановить сохранённые DNS-записи GitHub Pages. Завершить обновлением `HANDOFF.md` и `architecture/session-state.yaml`: SHA, URL, результаты проверок и фактический статус production/DNS. Не сообщать «опубликовано» до проверки основного домена.

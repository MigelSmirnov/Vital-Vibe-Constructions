## Разбор расхождения с main

До объединения: 134 коммита только в ветке сайта и 33 только в `main`. Эти числа описывали историю, а не 33 неперенесённых исправления.

В истории main были экспериментальный engineering-homepage, продвижение генерируемого сайта в корень GitHub Pages, исправления мобильной навигации и прямых ссылок на черновики. Последний коммит `b89f003` откатил эту линию целиком к дереву общего предка. Проверено локально:

```bash
git diff --exit-code 56ba3ec959a371ea1eb283d835ab5da7dc0be3d9 b89f003784b81ad6cf8efe672d6cc78446c07954
git rev-parse '56ba3ec959a371ea1eb283d835ab5da7dc0be3d9^{tree}' 'b89f003784b81ad6cf8efe672d6cc78446c07954^{tree}'
```

Оба дерева: `0d113e000709456dbb3e9f0808f038eeae6a6f8a`. Различий нет. Значит, из текущего main нет уникальных файловых изменений, которые нужно выборочно переносить. Отдельно возвращать отменённые исправления из промежуточных коммитов нельзя считать синхронизацией с main.

Обычное трёхстороннее слияние в отдельной релизной ветке прошло без конфликтов и без изменения дерева сайта. ## Правила продолжения

- `release/vps-migration` — интеграция и подготовка полного сайта к VPS.
- `agent/solar-collector-port` сохраняется как исходная версия; новые общесайтовые задачи туда не добавлять.
- Новые задачи — отдельные `agent/<task>` от согласованной актуальной базы, с PR в релизную ветку до завершения миграции, затем в main.
- Интеграцию релиза в main оформлять отдельным PR. Этот аудит не публикует main и не меняет настройки GitHub Pages.
- Для переноса передавать конкретный полный SHA завершённого релизного коммита. Не считать движущуюся вершину ветки неизменным релизом.
- Публиковать только свежий проверенный `.deploy-dist`; исходники и task не размещать на веб-сервере.
